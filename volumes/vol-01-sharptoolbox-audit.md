## 二、我做了什么（按结果分）

### 2.1 逆向与重装

| 动作 | 结果 |
|---|---|
| 11 仓库全量克隆 | 1768 文件 / 65MB |
| 抽出可运行机制并重装 | 本体运行时：读 YAML → 动态建库 → REST CRUD → 自动渲染表单页 |
| 实测 | **8 对象 / 12 表 / 中文表单标签由 YAML 直接驱动**（`合同名称`、`合同税率`…） |
| 生成器 | YAML → 185KB 自包含 HTML 调用链工作台；YAML → 123 节点/235 边离线知识图谱（1MB，0 外链） |

### 2.2 对抗性发现（本卷最重要的部分）

> **原作者的 engine，其只读 SQL 接口没有表名白名单。**

- 写操作**拦得住**（`UPDATE`/`DELETE`/`INSERT`/`DROP` 全被拒）
- **任意表读取拦不住** —— `SELECT name FROM sqlite_master` 可读出整个库的结构
- **可自行复现**：`python repro/verify_sql_gap.py`（退出码 0 = 发现成立）

**反差**：同一位作者在隔壁 `Onto-Contract` 仓库里**是有**白名单的。
→ 他的 engine 比他的 demo 更弱；**他的资产之间不共享安全基线。**

### 2.3 我自己的 bug（4 个，全部真跑才暴露）

| # | 现象 | 根因 |
|---|---|---|
| 1 | `can't open file 'C:\c\Users\...'` | git-bash 的 `pwd` 给 `/c/Users/...`，原生 Python 不做 MSYS 路径转换 |
| 2 | `FileNotFoundError: 找不到路径: 'SELECT contractNo...'` | `shift` 之后 `$1` 已是 SQL，却被当成参数目录 |
| 3 | kill 后端口仍在 200 | 杀掉的是 bash 外壳，`exec` 起的 Python **变孤儿继续监听** |
| 4 | 空闲端口本该 exit 0，实际 exit 1 | `set -euo pipefail` + `grep` 找不到返回 1 → 整个赋值被判失败，脚本提前退出 |

**1、2 的语法检查全部通过。** 静态审查看不出来。

### 2.4 我的一个假发现（必须记）

测前端托管时我 `from app import create_app` **又造了个 app 实例**，那上面没有模块级注册的路由 → `GET /` 返回 404 → **我差点报「原作者 README 关于 Flask 托管的说明是假的」**。

**真相是我用错了被测对象。** 改用正确实例后 `/` → 200，README 没错。

> **测错对象产生的"发现"比没测更危险——它带着看起来成立的证据污染判断。**

### 2.5 我的误报（第一版校验器）

第一版把 `permissions: ["*"]` 报成「悬空权限引用」。
实际那是通配符约定写法 → **假警报**。已修（加 `WILDCARDS` 白名单）并在案。

**先修自己的误报，再谈别人的缺陷。** 否则我就是一个只会指责别人的工具。

## 三、移植的校验体系（25 类规则，全部有命中证据）

移植自两处原作，**逐行读原文**（不是转述）：

| 模块 | 出处 | 规模 |
|---|---|---|
| 本体引用闭合校验 | `Onto-Model/validation_service.py` 9 条规则 1:1 + 超集 3 条 | 456 行 |
| 引用索引 / 删除影响分析 | `reference_service.py` 3 方法同名保留，索引 5→12 类 | 252 行 |
| 映射校验 + 可视化 | `mapping_engine.py` 3 函数 1:1 + 覆盖率检查 | 208 行 |
| 元模型文档对账 | **416 行 PowerShell → Python 完整移植，25 类规则一条不减** | 448 行 |
| 只读 SQL 守卫 | `sql_readonly_service.py` + 修 2 个绕过漏洞 | 207 行 |

**关键方法论**：不能只跑正例。25 类规则是用**故意违规的 fixture 分三轮喂出来的**，
每一类都有"这条规则真的开火了"的输出。

## 四、把规则本身也审了一遍——然后被自己的规则打脸

我拿自己重写的校验器，去跑原作者的"黄金范例"：

```
[WARN] TRACEABILITY_GATE_FAILED: 行为 Contract_Resubmit triggerType=USER_ACTION
       但没有任何 MU 操作功能点引用它（模型里有、界面上无入口）
... 共 5 条
结果：ERROR 0 / WARNING 5
```

**规范他写对了，机器兜底他缺了。**

顺着这条线还挖出结构性事实：**「逻辑删除」一个概念，全库 4 套实现**——
规范白纸黑字写「强制加 `flag` 字段」，而 engine 建的表里**根本没有 flag**，
它用的是 `status='已作废'`，且**没有作废态时直接物理删除**。

> **"强制"如果没有机器，就只是文档里的一个形容词。**
